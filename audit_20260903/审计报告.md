## 1. 未来函数排查（按要求逐项）

### 1.1 `shift(-1)`

- 全库正则 `shift\(\s*-` **0 处匹配**。
- 全部 `.shift()` 用例如下，均为**正向滞后（保守）或报表用途**，无一取未来：
  - `signals_v4.py:44` `price_changes.shift(skip_recent_days)`，`skip_recent_days≥0`（见 `signals_v4.py:42-43` 的参数校验），把最新观测往后平移，属于**更保守**的边界处理。
  - `signals_v4.py:59` `.expanding(...).mean().shift(1)`：预测缩放在当日只用到 t-1 及更早的信息。
  - `data_pipeline.py:182` `series.shift(lag)`：主力映射滞后 `lag` 天（代码默认 1，全部配置显式 `vendor_mapping_lag_days: 0`），`lag≥0`。
  - 其余（`workflow_v4_1.py:273/362`、`workflow_v4.py:686`、`analytics_v4_1.py:28/51/52`、`analytics_v4_2.py:243-244`、`costs_v3.py:67` 等）均为权益/持仓勾稽、状态分组或成本归因，不构成信号。

### 1.2 `iloc` 负索引

- 正则 `iloc\[[^]]*-` 命中 35 处，逐条核查均为下列两类，**无未来取值**：
  - **取序列末行（终端指标/最后一行规则）**：`analytics.py:32-33,48`、`analytics_v3.py:65,225`、`analytics_v4.py:35,216`、`reports_v3.py:175`、`reports_v4_1.py:94`、`workflow_v3.py:86,109`、`workflow_v4.py:453,455,690`、`workflow_v4_1.py:171,362`、`workflow_v4_2.py:28,151`、`costs_v3.py:73-76,121,223`。
  - **唯一索引防御性去重**：`engine.py:247,293,534,554,591`、`data_pipeline.py:335`、`engine.py:608,616` 均形如 `bar = self.bars.loc[key]; if isinstance(bar, DataFrame): bar = bar.iloc[-1]`。因 `bars` 已按 `(date, ts_code)` 去重，该分支正常不会触发，是防御性代码，不引入未来。
- 结论：`iloc[-1]` 全部合规；但建议把“防御性取末行”改为断言唯一（见《风险清单.md》#9）。

### 1.3 全量数据 `fit_transform` / 全样本标准化

- 正则 `fit_transform|\.fit\(|transform\(` **0 处命中 sklearn 缩放/训练**；仅 2 处 `transform` 为报表聚合：`analytics_v4_1.py:91`（groupby 字符串 join）、`analytics.py:162`（groupby sum）。
- 不存在“用全样本均值/方差标准化后回填历史”的泄漏模式。唯一的跨截面缩放 `causal_forecast_scale`（`signals_v4.py:50-60`）是**因果**的：当日 scaler 只基于 `t-1` 及更早的 expanding 均值，且带 `minimum_history_days=126` 的预热要求。
- 横向（cross-sectional）排名/选择（`signals.py:139-146`、`signals_v4_2.py:37+`）仅在同一天截面内比较，不跨期，合法。

### 1.4 执行时序复核（引擎层）

- 基类 `engine.py:106-210` 的主循环顺序：`① 执行昨日挂单（t 日开盘）→ ② 按 t 日结算/收盘 mark-to-market → ③ 计算权益 → ④ 计算目标（t 日收盘信息）→ ⑤ 挂单（t+1 日开盘执行）`。信号（`scores`）由 trailing rolling 得到（`signals.py:34-35`），vol/eligibility/liquidity 均为 trailing（`signals.py:95-106`、`signals.py:86-91`）。
- 每周信号日取 ISO 周最后一天（`signals.py:115-116` `W-FRI` 分组取 `index[-1]`），周内方向 carry 到下一个信号日，符合“周频调仓、次日开盘成交”。
- **结论**：执行层无未来函数。

### 1.5 残余风险（唯一需要长期警惕）

- `data_pipeline.py:372-379` `_next_contract_by_segment` 通过反向扫描整条换月序列确定 `FORWARD`（“下一主力合约”）身份，属未来换月信息；该字段只写入 `multiple_prices`（`data_pipeline.py:358-359`），**未进入信号/引擎**（grep 确认 `FORWARD` 仅用于存储与报表），当前无交易影响，属潜在地雷。详见《风险清单.md》#7。

## 2. 数据质量（tushare 下载可靠性与拼接正确性）

### 2.1 下载可靠性

- **优点**：`data_source.py:59-72` `_call` 对每个端点做 4 次重试 + 指数退避（0.5×2^attempt，上限 8s），调用间 `pause=0.15s` 限速；manifest 记录 token 指纹、api_calls、warnings、行数（`data_source.py:101-114`），可审计。
- **端点策略**：`fut_daily` 批量下载（每批 6 合约，`data_source.py:246-268` 附近），`fut_settle`/`ft_limit` 为 `optional=True`，首批次失败即禁用端点并记警告（`data_source.py:256-262`）。
- **缺陷**：
  1. **无交易日历核对**：下载/构建后不对交易日数、连续性做断言（v4_2 才引入 `calendar_v4_2.py:43-50` `audit_observed_dates`，且用于日历独立复算，而非主下载）。
  2. **合约内单日缺口静默跳过**：`build_panama_prices`（`data_pipeline.py:329-339`）对缺 bar 的日期直接 `continue`，产生 NaN/断点，不报错。
  3. **repair 只补“整段缺失”合约**：`data_source.py:117-150` `repair_missing_bars` 只对 `windows` 中完全不在 `bars` 的合约补采，不修复合约内的单日缺口。
  4. **费用下载脚本无重试**：`download_v3_fee_data.py` 单次 try、失败写 CSV 后不再重采（见 2.1 缺陷清单与《风险清单.md》#6）。

### 2.2 拼接正确性

- **bars 归一化**：`_normalize_bars` 对非正 OHLC 置 NaN、`drop_duplicates(["date","ts_code"], keep="last")`，字段映射（vol→volume、settle→settlement）正确。
- **结算/涨跌停/经济参数合并**：`data_pipeline.py:128-153` `_merge_daily_contract_data` 先各自 `drop_duplicates` 再 `merge(how="left")`，键 `["date","ts_code"]`，正确；contract_meta 以 `ts_code` 左连接，正确。
- **主力映射**：`build_mapping`（`data_pipeline.py:156-211`）优先用 tushare `fut_mapping` 前向填充（`.ffill()`）+ 可选滞后 + 到期强制换月（`_enforce_roll_deadline`，`data_pipeline.py:214-265`，仅用当日数据，`forbid_backward_roll` 禁止倒退换月）；无厂商映射时用 OI 兜底（`_oi_fallback_mapping`，`data_pipeline.py:268-306`，确认天数 2、切换比 1.10）。逻辑保守且正确。
- **Panama 换月拼接**：`build_panama_prices`（`data_pipeline.py:309-369`）在换月日回填 `_roll_gap`（`data_pipeline.py:382-396`，仅用 `previous_date` 及更早 ≤10 个交易日的双合约重叠价），完全后视，无未来信息。
- **流动性**：`signals.py:75-92` 用**主力合约**的 volume/oi 计算 20 日滚动中位数（trailing）。注意这是“主力合约流动性”而非“全品种加总流动性”，属建模选择，对绝对配置品种（RB/T/AL）无碍，对横截面选择是可接受的代理。

### 2.3 结论

拼接逻辑整体正确、后视合规；主要风险集中在“静默缺失”而非“错位拼接”。

## 3. 滑点与费用（核实交易成本模型，判定高估/低估）

### 3.1 手续费模型

- **v1/v2（基础引擎）** `engine.py:559-569`：
  ```
  reported = trading_fee*lots + lots*price*point_value*trading_fee_rate/10000
  commission = max(reported*1.2, fallback)
  fallback  = max(5元/手, 名义×0.0002)
  ```
  - 判定：**对国债期货 T 严重高估**（兜底 200元/手 vs 实际≈3元，约 60 倍）；对 RB 亦因兜底高估近 2 倍。详见《风险清单.md》#2。方向保守（成本高估→收益低估），但数量级错误。
- **v3+（正式模型）** `costs_v3.py:198-212` `FeeSchedule.charge`：
  ```
  exchange_fee = |lots| × (fee_per_lot + price×point_value×fee_rate)
  client_fee  = exchange_fee × client_multiplier   # formal=1.5
  ```
  `engine_v3.py:407/423-424` 将 `charge.client_fee` 计入 `commission`，`charge.exchange_fee` 仅作归因。
  - `fee_rate` 单位：tushare `trading_fee_rate` 为“万分之一”，除以 10000 后为比例（`costs_v3.py` 内注释，`engine.py:562-563` 同逻辑）；对 RB（名义≈3万、费率万分之一）得 ≈3元/手，与市场一致。
  - `build_fee_rules`（`costs_v3.py:30+`）把逐日参数压缩为带生效区间的规则，`_lookup`（`costs_v3.py:214-224`）按 `(合约/品种, 日期, 开平类型)` 命中，支持 `close_today` 代理（T/SC 平今免费，其余按普通费代理，并标记“最新标准回溯为代理历史”）。
  - 判定：**v3+ 手续费模型为合理偏保守的研究级近似**。已知近似：① 客户倍数 1.5 是“交易所费×1.5”的线性近似，真实经纪加价多为固定每手小额，对低费率品种可能略低估、对高名义品种略高估，但框架已用 1.2/1.5/2.0 及盈亏平衡 1.0–12× 做敏感性（`workflow_v3.py:29-31,117` 与 `configs/v3` 相关段）。② 平今费为代理值，非逐日真实平今费。

### 3.2 滑点模型

- **成交价**：`engine_v3.py:438-452` 分层基础 tick（正常：高流动 1t / 其他 2t；压力：2t / 3t），`engine_v3.py:392` 换月额外 +1t，`engine_v3.py:388` 参与率冲击（>1% 加 1t、>3% 加 2t），`engine_v3.py:393` 合成 total_ticks，`engine_v3.py:396` `_adverse_grid_price` 向不利方向取整到 tick。
- **成本金额**：`engine_v3.py:417-419` `slippage_cost = |qty| × |fill−open| × point_value`，同时记录 `base/roll/impact/total` tick 分项供归因。
- **v4_1 成本族**：`engine_v4_1.py:44-53` 定义 C0–C7，`_base_ticks`（`engine_v4_1.py:74-83`）用 `max(0, tier + base_shift_ticks)`（C2=−1 被下界 0 截断，故不存在“负滑点/成交改善”的乐观场景，只是比 C3 少 1 tick）；官方 `C3`、压力 `C7`（fixed 3t）。
- 判定：**滑点模型方向正确、整体合理偏保守**（始终向不利方向 + 换月 + 冲击；不会出现成交改善）。潜在低估点：未建模队列/限价单未成交的隐性成本、涨跌停极端日的流动性枯竭（已通过 `reject_locked_limit` 与 `adverse_limit_lock` 部分缓解）。

### 3.3 综合判定

| 版本 | 手续费 | 滑点 | 判定 |
|---|---|---|---|
| v1/v2 | 名义费率兜底，**T 高估≈60×、RB≈2×** | 固定 1–2 tick 逆向 | 手续费高估（数量级错误，方向保守） |
| v3/v4/v4_1/v4_2 | tushare 规则×1.5 | 分层 1–3t + 换月 1t + 冲击 0–2t | 合理偏保守 |

## 5. 其他值得审计的要点

1. **样本外纯度（方法学，最高优先）**：验证期被用于 21 策略择优与 sleeve 推荐，报告验证期 Sharpe 有乐观偏差 + 多重比较风险（`analytics_v4_1.py:265` 已自我披露）。见《风险清单.md》#4。
2. **“滚动下一年拼接”是切片而非 walk-forward**：`rolling_walk_forward_v4` 仅把**固定策略**权益曲线按年切成训练/测试桶用于展示，并不重训练；名称易误导读者以为做了真正的滚动优化。建议更名或在文档中明确。
3. **确定性**：`engine.py:106` 起主循环排序日期、`sorted(all_contracts)`、dict 插入有序，数值确定；v3 仅行序受 set 迭代影响（v4 已规范化）。
4. **经济参数回退**：`universe.py:33-48` 的 `FALLBACK_ECONOMICS` 为静态近似（保证金率随时间变）；真实值依赖 `fut_settle`。若 `fut_settle` 缺失，保证金回退只影响约束缩放（不影响 PnL），但 `FALLBACK_ECONOMICS` 缺品种的 1/1/0.18 静默默认会直接影响 PnL（见 #1 高风险项）。
5. **年化精度**：`len/252` 年化对中金所实际交易日（约 243）有轻微偏差（见 #10）。
6. **平今费代理**：`close_today_missing_policy: explicit_proxy`（`configs/v4_2:71`）把最新标准回溯应用，且平今费用普通费代理（T/SC 平今免费已特判）；跨期精确平今费未建模，属已知近似。
7. **未成交订单**：`unfilled_mode` 支持 `retry` 与 `cancel_recalculate`（`engine.py:126`、`engine_v3.py:56+`）；v3/v4 基线用 `cancel_recalculate`，语义清晰。

## 6. 结论与整改优先级

1. **立即**（高风险、静默错误）：#1 合约经济参数静默回退 → 改为 fail-fast。
2. **短期**（中风险）：#2 修正 v1/v2 兜底费率（或废弃）；#3 给费用模型加降级；#4 增设真样本外期/多重比较校正；#5 下载后做日历核对。
3. **中期**（低风险，提升可维护性）：去复制粘贴、去 `import *`、去硬编码路径/日期、修分层倒置。
4. **保持**：会计勾稽门、seed 记录、v4 输出规范化、成本敏感性矩阵——这些是本框架可复现性的真正资产。

**总体评价**：本回测框架在“未来函数”这一最致命维度上**表现干净**（结论性），数据拼接与执行时序合规；交易成本模型 v3+ 合理偏保守、v1/v2 存在国债手续费高估的数量级缺陷；主要改进空间在方法学（样本外纯度）与工程可维护性（版本化重复、硬编码、静默回退）。
