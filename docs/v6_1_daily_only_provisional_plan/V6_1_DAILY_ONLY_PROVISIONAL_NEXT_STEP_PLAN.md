# v6.1 日线数据限定版下一步研究与执行方案

版本：v1.0  
状态：`SUPERSEDED_BY_V6_1_EXECUTION_TASK_v1_1_FINAL`  
权威说明：本文保留为设计历史，不再作为执行权威。后续实施唯一完整规范为同目录的 `V6_1_DAILY_ONLY_PROVISIONAL_EXECUTION_TASK_v1_1_FINAL.md`。  
建议运行标签：`v6_1_PROVISIONAL_DAILY_ONLY`  
适用前提：没有 `ft_limit`、`ft_mins` 和可完整核验的逐笔/盘口数据，只有期货日线 OHLC、成交量、持仓量、结算价及现有历史缓存。

## 1. 决策结论

建议保留 v6 v1.4 的 `BLOCKED_BEFORE_A01`，不修改其注册表、闸门、代码、数据和输出。另建 v6.1 日线限定研究分支，并在所有配置、表和报告中强制标记：

```text
research_status = PROVISIONAL_DAILY_ONLY
execution_evidence_level = DAILY_BAR_PROXY
official_limit_coverage = NOT_AVAILABLE
intraday_session_verified = false
queue_and_fill_probability_observed = false
```

v6.1 的目的不是产生“真实执行回测”，而是在日线数据约束下回答：原有策略结论对几种方向明确的成交代理是否稳健，以及可能的合理结果区间有多宽。

## 2. 为什么不能直接把 v6 闸门删除

缺少 `ft_limit` 时，无法可靠知道每个订单形成前已经生效的涨跌停价格，也无法完整处理临时调板、连续停板、节假日、交割月和特殊合约规则。

缺少 `ft_mins` 时，无法核验日线 `open` 究竟对应夜盘首开、日盘首开还是供应商的其他会话定义，也无法观察盘口价差、排队、开盘集合竞价、成交先后顺序和订单在日内何时获得成交。

因此，日线 OHLC 可以描述当日价格范围，但不能证明：

- 订单在开盘时一定可以成交；
- 某个 `high == low` 日一定是交易所涨跌停锁板；
- 订单在触及某个价位时前方队列有足够成交量；
- 固定 1—3 tick 与参与率冲击没有重复计价；
- 日线开盘价的夜盘/日盘归属。

删除这些限制却继续使用“正式”“真实”“官方限价”等措辞，会提高结果的表面精度，但不会提高证据质量。

## 3. 日线限定版的核心修改

### 3.1 执行时间语义

正式基准建议使用：

```text
信号形成：交易日 t 完成周收盘后
订单形成：t 收盘后
尝试成交：下一交易日 d 的 vendor_daily_open
日线 open 含义：供应商定义的该 trade_date 第一开盘记录，夜盘/日盘归属未验证
```

不再把它描述成“次日日盘开盘”或“已核验的第一交易时段开盘”。只要订单使用的信号和目标全部在 d 的 vendor daily open 之前形成，因果顺序仍可保持；缺失的是会话语义与微观成交真实性，不是信号层面的未来函数许可。

同时固定一个执行时点压力场景：下一交易日收盘代理。该场景用于衡量“日线 open 语义错误或开盘不可成交”可能造成的方向性影响，不用于择优。

### 3.2 不再声称识别真实涨跌停

v6.1 不建立 `REJECTED_LIMIT` 真值事件，改用下列独立原因码：

```text
DAILY_ONE_PRICE_DIRECTIONAL_PROXY_REJECT
DAILY_ONE_PRICE_ALL_SIDE_STRESS_REJECT
DAILY_BAR_MISSING_REJECT
DAILY_VOLUME_ZERO_REJECT
DAILY_PROXY_FILLED
```

报告中禁止把这些事件简称为“真实锁板”。

### 3.3 high/low 的合法用途

`high/low` 只能在订单已经于当日开始前形成后，用作当日实现成交结果的事后日线代理；不得进入信号、目标头寸、候选品种、开盘前限价或交易方向的计算。

这属于“订单已先形成，随后观察整日结果”的执行模拟，不属于信号未来函数。但由于不知道日内路径与成交时刻，任何依赖整日 OHLC 的成交只能标记为 `EX_POST_DAILY_EXECUTION_PROXY`。

### 3.4 一字板代理的方向规则

当 `high == low` 时，以当日单一价格相对前结算价的方向分类：

```text
one_price > pre_settle：上涨单一价格日
one_price < pre_settle：下跌单一价格日
one_price == pre_settle 或 pre_settle 缺失：方向不明/无交易代理
```

正式日线代理场景中：

- 上涨单一价格日：拒绝新增买单和买入平仓单；卖单允许按单一价格成交；
- 下跌单一价格日：拒绝新增卖单和卖出平仓单；买单允许按单一价格成交；
- 方向不明、成交量为零或日线缺失：双向拒绝；
- 不把 `high == low` 本身称为涨跌停，也不用于推导涨跌停幅度。

该规则可能把极低流动性的单一成交日误判为不可交易，也可能高估有利方向订单的成交能力，必须配合上下界场景解释。

### 3.5 非单一价格日

若 OHLC 完整、成交量大于零且 `high > low`：

- 基准场景按 vendor daily open 加不利整数 tick 成交；
- 成交价格必须落在最小变动价位网格；
- 继续执行原 5% 成交量参与率上限和部分成交；
- 不因当日后来触及某价格而回填开盘成交；
- 如果不利滑点价超出当日 `[low, high]`，按“不可证明开盘可成交”拒单，而不是把价格裁剪回区间。

最后一条较保守，目的是避免用当日最高/最低价制造并不存在的平滑成交价。

### 3.6 P&L 记账

- vendor daily open 成交代理：成交后按该日收盘/结算进行持仓盈亏；
- 下一交易日收盘代理：在该日收盘完成交易，新的持仓风险从下一交易日开始，不能同时获得该日开盘至收盘盈亏；
- 单一价格日允许成交的一侧，因为整日价格不变，当日不产生虚构的开盘至收盘利润；
- 拒单不改变持仓，下一交易日按既定的取消并重算规则生成新订单；
- 任何场景都不得根据当日收盘后的信息反向改变当日开盘前的信号或目标。

## 4. 预注册的有限执行矩阵

只对两个固定策略运行：

1. `reference_v3_252`；
2. `sleeve_20skip5_250_equal_risk`。

建议最多运行 12 个完整历史场景，不做参数笛卡尔积：

| 组别 | 场景 | 执行代理 | 单一价格日政策 | 滑点 | 用途 |
|---|---|---|---|---|---|
| R | R01/R02 | vendor daily open | 完全沿用旧路径 | 原 v3 正常滑点 | 兼容复现，不作新结论 |
| P0 | P01/P02 | vendor daily open | 有日线即假定可成交 | 原正常滑点 | 偏乐观上界 |
| P1 | P03/P04 | vendor daily open | 方向性拒单 | 原正常滑点 | 正式日线代理基准 |
| P2 | P05/P06 | vendor daily open | 所有 `high==low` 双向拒单 | 原正常滑点 | 偏保守执行压力 |
| S1 | P07/P08 | vendor daily open | 方向性拒单 | 固定 1 tick | 低成本边界 |
| S3 | P09/P10 | vendor daily open | 方向性拒单 | 固定 3 tick | 高成本边界 |
| C | P11/P12 | next trade date close | 方向性拒单 | 原正常滑点 | 执行时点压力 |

每一行两个场景分别对应 v3 参照与 20skip5/250 袖套。所有场景必须预先运行并保留，不得只报告收益最好的代理。

正式解释优先比较 P0、P1、P2 三种成交可得性假设；S1/S3 只回答无法校准盘口时成本区间有多宽；C 只回答执行时点变化是否改变结论。

## 5. 保证金数据缺口的同步处理

当前保证金也没有达到 v6 正式“官方或因果推导”覆盖阈值。v6.1 建议：

- 保留现有逐日可得供应商保证金；
- 缺失时使用 v3 已冻结的品种 fallback margin；
- 客户保证金继续乘 1.25；
- 保留商品 65% 保证金利用率和 8 倍名义杠杆目标约束；
- T 继续不受商品名义杠杆约束，但仍进入总 78% 目标约束；
- 所有 fallback 行标记 `PROXY_MARGIN`；
- 日终超限只记录、下一标准目标计算降险，不实施强平；
- 报告保证金约束命中率，并额外做冻结头寸路径的 `proxy margin ×1.25` 压力诊断，不把该诊断作为新策略。

这套保证金只能用于控制回测风险暴露，不能声称复原了历史经纪商追保或强平行为。

## 6. 日线数据质量新闸门

在任何完整历史运行前必须通过：

1. 每个合约交易日键唯一；
2. `low <= min(open, close) <= max(open, close) <= high`；
3. 价格落在最小变动价位网格，或明确记录供应商舍入异常；
4. volume、OI 非负；
5. vendor daily open、close、pre_settle 的覆盖率按年份、品种、交易所披露；
6. `high==low` 按成交量、涨跌方向、品种和年份输出全部事件，不预先命名为锁板；
7. 未来追加数据不改变历史信号、目标、订单形成日和一字板代理分类；
8. 当日 high/low 的任何扰动不得改变当日开盘前信号和目标；
9. 收盘执行场景不得获得执行当日开盘至收盘盈亏；
10. 滑点、市场冲击和换月额外 tick 继续分别记账且不重复扣除；
11. 账户权益与逐品种 P&L、手续费、滑点、冲击、换月成本满足逐日勾稽；
12. 完整历史 attempt 使用独立 v6.1 账本，不写入 v6 v1.4 的 attempt ledger。

## 7. 必须输出的诊断

- 三种单一价格日政策下，拒单数量、方向、品种、板块、年份和订单原因；
- P0→P1、P1→P2 的首个路径分歧日期和后续权益反馈；
- vendor open 与 next-close 的成交价格、持仓起效日、换手和成本差异；
- 1 tick、正常滑点、3 tick 的净收益与最大回撤区间；
- 被拒订单中开仓、平仓、反手、换月旧腿和新腿的数量；
- 换月旧腿无法成交时是否阻止新腿开仓；
- volume/OI 参与率限制产生的部分成交和未成交手数；
- 保证金供应商数据与 proxy 数据的使用占比；
- 全样本、样本内、验证期、分年度、分板块和分品种结果；
- 与 v3/v4.2 的差异必须拆成执行代理直接差异与权益—仓位反馈差异。

## 8. 结果判定规则

只有同时满足以下条件，才能说“策略在日线执行假设下具有稳健性证据”：

1. P0、P1、P2 的全样本和验证期结论方向一致；
2. 1 tick、正常滑点和 3 tick 下没有关键结论反转，或反转边界被明确量化；
3. vendor-open 与 next-close 不产生完全相反的策略排序；
4. 结果不依赖少数单一价格代理事件；
5. 账户勾稽、前缀不变和成本唯一扣除测试全部通过；
6. 报告不把代理结果描述成真实成交、真实涨跌停或真实强平结果。

若上下界差异足以改变策略结论，应停止在“数据不足以判断”，而不是选择更有利的代理场景。

## 9. v6.1 可以和不能支持的结论

### 可以支持

- 在固定日线执行代理下的策略相对表现；
- 结果对一字板代理、1—3 tick、执行时点的敏感度；
- 哪些年份、品种和订单类型最依赖成交假设；
- 成本和未成交机制是否足以推翻快慢周期组合结论；
- v3 与 20skip5/250 袖套在统一日线路径下的相对稳健性。

### 不能支持

- 历史订单真实成交率；
- 真实涨跌停拒单数量；
- 夜盘首开或日盘首开的精确归属；
- 开盘集合竞价和盘口排队结果；
- 真实 bid-ask spread、冲击成本或换月可成交量；
- 经纪商真实保证金、追保和强平路径；
- 适合直接用于实盘下单的执行参数。

## 10. 推荐实施顺序

1. 新建 `V6_1_MACHINE_REGISTRY.yaml`，冻结上述 12 个场景、原因码和停止条件；不得修改 v6 v1.4 registry。
2. 建立日线数据审计表和所有 `high==low` 事件账本。
3. 先实现并测试 vendor-open 与 next-close 两套记账时点，特别检查 next-close 不获得当日收益。
4. 运行 R01/R02 兼容闸门；若关键权益、订单和持仓无法解释地偏离，停止。
5. 依次运行 P0→P1→P2，再运行 S1/S3 和 C；不得中途增加场景。
6. 生成独立时间戳输出、CSV/pickle 底层表和中文报告。
7. 报告结论统一加 `PROVISIONAL_DAILY_ONLY` 水印或状态字段。
8. 未来取得 `ft_limit` 或分钟数据后，重新回到 v6 v1.4 Phase 1A；v6.1 结果不得自动升级为正式基准。

## 11. 最终建议

在现有数据条件下，最合理的前进方式是运行 v6.1，但把它定位成“成交假设稳健性研究”，而不是“修复后的真实回测”。正式日线代理使用方向性单一价格日拒单；“全部成交”和“所有单一价格日双向拒绝”分别作为乐观与保守边界。继续使用 vendor daily open，但删除未经验证的夜盘/日盘表述，并用 next-close 场景检验执行时点敏感性。

如果 P0/P1/P2 与 1/3 tick 的结论一致，日线数据足以支持策略层面的初步判断；如果结论随代理规则改变，则应把取得逐日限价和分钟/盘口数据列为继续研究的必要条件。
