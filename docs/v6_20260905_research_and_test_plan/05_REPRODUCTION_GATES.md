# v6 复现、纠错和发布闸门

## 1. 通用比较规则

离散对象必须逐键完全一致：日期、品种、合约、方向、手数、订单原因、成交/拒单状态。数值容差：

| 对象 | 容差 |
|---|---:|
| 信号/波动率/缩放系数 | `max_abs_diff <= 1e-12`，或记录平台浮点 ULP 差异 |
| 价格 | 不超过 `1e-10` 且必须在 tick 网格 |
| 持仓手数 | 0，必须完全一致 |
| 单笔/逐日金额 | `<= 0.01 元` |
| 全期账户勾稽 | `<= 0.01 元` |
| 哈希 | 完全一致 |

不能通过放宽容差、删除差异行、改变排序或只比较最终净值绕过闸门。

## 2. G0：注册、隔离和输入冻结

启动任何 A 组完整历史运行前，必须同时构建并冻结两个不可变输入快照：

1. `legacy_compat_snapshot`：只读承载 A01—A05 所需的旧市场、旧日历、旧规则和旧行为；
2. `corrected_v6_snapshot`：承载 A06 及 B—I 所需的共享市场载荷、修复日历、手续费、限价、逐日保证金、单位和来源规则。

二者的 `snapshot_id`、父来源和差异字段白名单必须写入 manifest。Phase 1 的规则建设和 G0-DATA-FEASIBILITY 是冻结这两个快照的一部分，不得在 A 组运行后再补建或覆写规则。执行前还必须保存：

- 本目录全部 v6 计划文件的 SHA256；
- `V6_MACHINE_REGISTRY.yaml` 解析成功，恰有 44 个唯一场景、连续顺序 1..44、22 个唯一基础策略，并与人类注册表逐字段一致；
- 独立 `configs/five_sector_momentum_v6.yaml` 及解析后配置；
- 机器/人类场景注册表及最大运行数；
- 两个输入快照的数据、日历、费用/保证金/限价规则哈希；
- Git commit/dirty 状态、Python 和依赖精确版本；
- 随机种子、Bootstrap 种子和执行命令；
- 历史正式/失败/作废目录白名单。

旧目录发生写入、注册表晚于首个结果时间、配置未解析落盘、任一输入快照在 A01 启动后变化，均为失败。

### G0-DATA-FEASIBILITY：完整回测前的数据可行性预检

在启动 A01 之前，先实际构建候选规则表并对历史正式输出的冻结订单/持仓键运行覆盖脚本，机器判定：

- 五所 10 合约 `ft_limit` 权限探针已经明确区分有数据、无权限、未上市和真实空区间；
- RB/SC/M/TA/T 各 15 日的日线 open—分钟首开—交易日归属核验全部匹配；
- 所有比例手续费字段单位已登记，且每类至少一个官方锚点通过；
- A01/A04 冻结订单键的 `OFFICIAL_DAILY/OFFICIAL_RULE_DERIVED` 限价覆盖实际等于 100%；
- A01/A04 冻结持仓的方向性保证金官方/推导绝对名义敞口覆盖在全组合、商品合计和 T 合计分别实际≥95%；有暴露品种年度≥80%，关键临时提保暴露日=100%；
- 逐合约 endpoint 权限、空返回和官方规则替代路径清楚；
- v6 共享市场字段可以与冻结历史快照逐键相同。

这是数据/权限预检，不看新绩效、不计完整历史引擎运行。“已有来源/以后可补”不能代替实测覆盖。任何一项不达标，直接输出 blocker，禁止消耗兼容运行额度。

## 3. G1：规范数据、端点和规则覆盖闸门

- `fut_settle`、`ft_limit` 逐合约调用；
- 空响应、权限失败、字段缺失和重复冲突有明确状态；
- v6 行情、合约、映射和 Panama 共享字段与冻结旧快照逐键相同；
- 手续费、保证金和限价每条规则可追溯到 URL/文件/代理理由；
- 规则优先级、单位、生效区间和舍入方式唯一；
- 所有潜在成交可命中手续费规则；
- 所有订单日有可接受限价；
- 所有持仓/拟成交日有保证金或显式回退；
- manifest 行数必须与落盘文件一致。

关键端点 0 行却 `warnings=[]` 直接失败。若共享市场字段需要修正，当前计划停止，不得把数据变化混入 B01/B02。

用 v6 `compatibility` 模式依次复现：

1. `reference_v3_252`；
2. v4.2 G1 `single_20_skip5`；
3. v4.2 G2 `single_250`；
4. v4.2 S1 固定 50:50 袖套；

A06 另做日历单因素桥接：除日历、由其直接引起的信号/订单及后续账户路径外，输入市场数据、成本和约束规则必须和 A01 一致。

G2 只证明迁移没有无关漂移，不认可旧缺陷。任何输出必须带兼容缺陷标记。

## 5. G3：手续费闸门

### 5.1 冻结路径验证

先用旧 fills：

- 旧规则逐笔复算必须和旧账一致；
- 仅把正确费率规则替换后，逐笔差额和按品种/年份/交易类型汇总一致；
- 冻结路径权益变化必须恰好等于手续费差，不得混入滑点或仓位反馈。

### 5.2 手算锚点

至少覆盖：

- RB 基准月与非基准月的比例费；
- SP 历史费率变更边界；
- AL 固定每手费；
- SC 固定每手费和平今规则；
- T 固定 3 元/手及客户倍数；
- 开仓、平昨、平今、跨零、部分成交、换月双腿。

每个锚点保存公式、原始单位、官方来源、生效日、期望值和实际值。

### 5.3 动态重跑

对 v3 和 S1 各运行一次“只修手续费”场景。报告必须把：

```text
最终权益差 = 冻结路径直接手续费差
           + 权益变化引起的仓位/成交反馈
```

两项分开列示且必须精确加总；所谓残差只能是≤0.01元的数值勾稽误差。临时重跑的 43,694,213.86 元净利润等只作锚点，不作通过条件。

## 6. G4：因果限价与订单状态闸门

定向验证：

- BUY@上限拒绝，SELL@下限拒绝；
- 上限时 SELL、下限时 BUY 属价格侧可成交方向，但仍受成交量、风险和保证金约束；开仓/平仓属性不能覆盖价格方向；
- 非限价开盘按正常滑点执行；
- 成交价不得越过官方上下限；
- 全部有交易合约日必须满足因果推导上限不低于 observed high、下限不高于 observed low；这只是必要条件，不能替代官方来源；
- 限价相等以整数 price tick 判断；滑点截断记录 requested/executed/limit-clip；
- 限价字段只由开盘前已知数据得到；
- 跨零先平后开；平仓拒绝时不开反向新仓；
- roll 旧腿拒绝时新腿不先完整开仓；
- 部分 roll 只匹配已完成旧腿风险；
- 拒单不收费，不减少/增加持仓；
- 次日重算不沿用已经过期的旧数量。

主力映射 12 个 `high==low` 形态日、其中旧路径 7 段成交/4 段逆向成交，以及 RU2505 2025-04-07 换月旧腿组成固定挑战集。每个点必须人工核验官方/因果限价、交易日和订单腿；只有来源确认且实际订单处于逆向限价侧时才以 `REJECTED_LIMIT` 为期望。不能把 12 天当成官方全历史锁板总数，也不能把预期“应该拒绝”脱离订单方向硬编码。

若只能得到 `DIAGNOSTIC_PROXY`，G4 不通过；允许输出代理敏感性，不允许进入正式基准。

## 7. G5：逐日方向性保证金闸门

- T 的单位转换由 registry 驱动，2.0→0.02；
- 多头/空头分别使用 long/short rate；
- 生效日边界和 as-of 正确；预交易只用开盘前已知率与拟成交价，日终占用才用当日结算价和日终有效率；
- 客户代理倍数 1.25 单独记录；
- 缺失回退只在缺失处触发，不得用 `max` 覆盖低于静态值的真实率；
- 平仓永不因保证金不足被阻止；
- 开仓按整数手缩减；
- 商品上限不作用于 T，但账户占用仍记录；
- 冻结持仓重算与引擎 margin snapshot 一致；夜盘按下一交易日正确归属。

官方/官方推导覆盖率按 `Σ abs(lots)×settlement×multiplier` 的绝对名义敞口加权，在 A01/A04 冻结持仓预检并在 B07/B08 实际持仓确认。覆盖率必须同时满足：全组合≥95%、商品合计≥95%、T 合计≥95%。另按 `instrument×完整自然年` 输出覆盖；任何有非零敞口的品种年度低于 80% 时标 `PROVISIONAL`，禁止正式发布。凡交易所已知临时提保、节假日或交割特殊保证金生效日实际存在持仓/拟成交，官方/官方推导覆盖必须为 100%，不得被年度平均掩盖。

## 8. G6：账户和成本勾稽闸门

对每个场景同时通过：

0. 每个订单事件和结算日的在线核心不变量；任一失败立即中止，不能等场景末尾；
1. 事件账本自身逐日勾稽；
2. 独立 pandas/numpy 逐合约复算；
3. 冻结 fills 的费用复算；
4. 总账户与品种/板块/多空贡献之和；
5. 滑点分项与总滑点；
6. 成交、持仓和保证金连续性；
7. 内部袖套虚拟目标与真实净订单成本隔离。
8. 65%/78% 只能表现为目标仓位缩减与日终实际超限诊断，不能生成新增强平订单；若 `equity<=0`，必须写 `ACCOUNT_INSOLVENT`、保留部分账本并停止，禁止外部注资和合成有限责任评价曲线。

最大金额残差必须≤0.01元；关键数量残差必须为0。滑点不得既进入成交价又从现金再次扣除。

A01—B08 的 `ACCOUNT_INSOLVENT` 事件数必须为 0。非零不是可忽略的极端观察，而是会破坏单因素归因和完整策略家族的阻断事件。

每个 B—H 场景完成后立即运行该场景适用的 G6 子检查；不能等所有业绩跑完再发现账户失败。

## 9. G7：未来函数和前缀不变闸门

对每个阶段截断历史，再追加未来数据，历史共同区间必须不变：

- 交易日历的完整周/月标记；
- 主力映射和最晚换月；
- Panama 价格和 roll gap；
- 点差波动率、单/多周期 forecast 与 scaling；
- 20 日流动性中位数和 eligibility；
- 252 日协方差统一缩放；
- 63 日实现波动反馈和紧急减仓状态；
- 横截面资格、排名和 runner-up；
- 内部目标、净目标、订单形成日；
- 手续费、保证金和限价规则 as-of；
- 订单在 t+1 之前不得成交。

报告域 `FORWARD_CONTRACT` 字段必须通过依赖图证明不能流入交易域。

每个 B—H 场景完成后立即运行固定边界和随机截点的 G7 子检查；全局 G7 汇总不能替代场景即时检查。

## 10. G8：确定性和发布闸门

只对注册的两个代表正式场景做完整历史跨进程复跑：B07↔I01、B08↔I02。I01/I02 分别与原场景拥有相同 `economic_config_hash`；该哈希排除 `run_id,scenario_id,output_path,started_at,attempt_id,replicate_of` 等运行身份字段。完整 manifest 哈希预期不同。事件表使用不含运行身份的确定性 `business_event_key` 比较，`run_event_id` 只要求各运行内唯一。其他场景用事件重放、CSV/pickle 和排序哈希确定性检查，不再消耗完整历史运行：

- 所有主键集合一致；
- 排序后离散表逐位一致；
- 浮点/金额在既定容差内；
- CSV 与 pickle 内容相同；
- 跨进程表身份比较使用 `canonical_json_rows_v1` 内容哈希；不得因 pickle/pandas 字节不同误报业务差异；
- 测试清单实际存在，计数与报告一致；
- 场景 attempt/effective/invalid 计数一致；
- 报告每个表能定位到底层文件；
- 技术闸门通过后先保持 `COMPLETE_NONCANONICAL`；项目所有者/指定复核人签署后，项目级 `outputs/CANONICAL_V6.json` 才可原子指向一个全部闸门通过的目录及其 manifest 哈希。

## 11. 闸门状态机

```text
G0 → G0-DATA-FEASIBILITY → G1 → G2 → G3 → G4 → G5 → G6 → G7 → G8
```

某个闸门失败后：

1. 当前运行目录的 `RUN_STATUS.status` 标记为固定枚举 `FAILED_GATE`，并在独立字段 `failed_gate_id` 写具体闸门（例如 `G4`）；
2. 保留日志、差异表和已产生底层文件；
3. 禁止继续后面的业绩场景；
4. 修复必须建立新运行目录；
5. 注册表中的失败 attempt 仍计入尝试数；
6. 最终报告不得隐藏失败运行。

## 12. 闸门完成定义

“代码已改”“测试大部分通过”或“最终收益方向相同”都不等于完成。只有自动测试、手算样例、生产覆盖、独立复算、差分归因和发布文件同时存在，才可关闭问题。
